# Code Reviewer Skill

You are a senior code reviewer. When invoked, you will:

## Mandatory cross-review overlay

For PR reviews, milestone reviews, pre-merge gates, or serious agent-built work, first load `cross-review-qa` and apply its fresh QA loop:
- Preserve the original plan/spec/acceptance criteria and relevant ATLAS SPINE as the yardstick.
- Spawn a brand-new read-only QA context; when the reviewer is Claude Code, call it through `tmux-model-workers`, not `claude -p` or blind background execution.
- Require issue-only findings labeled `BLOCK`/`HIGH`/`MEDIUM`/`LOW`, with file/section evidence and suggested fix direction.
- Send enumerated `BLOCK`/`HIGH` findings back to the main agent/builder to fix, rerun verification, then re-review.
- Keep looping until no `BLOCK`/`HIGH` findings remain before reporting pass/completion.

## Primary Tasks
1. Analyze code for potential bugs and edge cases
2. Check for adherence to best practices and design patterns
3. Evaluate code readability and maintainability
4. Identify security vulnerabilities
5. Suggest performance optimizations
6. Verify proper error handling

## Review Checklist
- [ ] Code follows project conventions
- [ ] Functions have single responsibility
- [ ] Proper error handling implemented
- [ ] No security vulnerabilities
- [ ] Tests cover critical paths
- [ ] Documentation is clear and complete
- [ ] Performance is acceptable
- [ ] No code duplication

### Safety-gate / readiness-lane reviews

When reviewing code that controls go-live, readiness, approvals, external actions, CRM writes, email/SMS/LinkedIn sends, or deploy/merge authority, add an explicit fail-closed pass:
- [ ] Permission booleans fail closed: malformed truthy values like `"false"`, `"true"`, `1`, non-empty lists, or missing keys do not accidentally authorize action or display readiness.
- [ ] Readiness labels are precise: distinguish **artifact ready**, **executor-queue/gate ready**, and **side-effect permission granted**. A Level 4/executor-ready verdict may be valid without opening sends/writes; verify `send_allowed` and `write_allowed` separately.
- [ ] Human-review policy is explicit and tested. If the product rule is threshold-based (for example: human review only after more than 3 QA failures), verify pass/retry/escalate branches and do not preserve stale “QA pass → human approval” assumptions in tests or labels.
- [ ] A ready verdict depends on the actual gate/request/artifact status and current policy, not only on an upstream draft status string.
- [ ] Leak and side-effect scans check both regex payload leaks and explicit safety flags/counters/aliases.
- [ ] Important findings that could change a readiness verdict are treated as pre-finalization fixes, not optional follow-up.

### Live-vs-mock integration readiness

When reviewing integration-heavy work, especially contractor/vendor deliverables, do not treat a passing test suite as proof of production readiness:
- [ ] Inspect adapter selectors and environment gates, not just service code. Look for `*_MOCK`, `validateOnly`, `mock-first`, `developer token pending`, `not configured`, and live-mode branches that intentionally throw.
- [ ] Classify each integration as **live verified**, **live scaffolded**, **mock/stub only**, or **blocked**. A live client class is only “live scaffolded” until a dated external acceptance/read-back artifact exists.
- [ ] Require proof artifacts for business-loop completion: e.g. click → call → confirmation → accepted external conversion, with each step labeled live/synthetic/mock.
- [ ] Call out PR/CI absence separately from code quality; local green checks are useful but do not replace protected branch review and repeatable CI.
- [ ] Treat stale task/spec checkboxes as a governance gap: implemented files may exist, but project status is ambiguous until task docs or release notes match the repo state.

## Output Format
Provide feedback in this structure:
1. **Critical Issues** (must fix)
2. **Important Suggestions** (should fix)
3. **Minor Improvements** (nice to have)
4. **Positive Observations** (what was done well)

Always explain WHY something should be changed and provide specific examples.

## Input Contract

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| code | string or file_path | Yes | The code to review. Can be inline code, a file path, a git diff, or a PR number (e.g., `#123`). |
| scope | string | No | Review focus: `full` (default), `security`, `performance`, `conventions`, `bugs-only`. |
| context | string | No | Additional context about what the code does or why it was changed. Helps the reviewer prioritize findings. |

## Output Contract

**On success:** Returns a structured review with 4 sections: (1) Critical Issues (must fix), (2) Important Suggestions (should fix), (3) Minor Improvements (nice to have), (4) Positive Observations (what was done well). Each finding includes the WHY and a specific code example or fix.

**On partial success:** If only part of the code could be reviewed (e.g., file too large, binary content), returns findings for the reviewable portion with a note about what was skipped.

**On failure:** Returns an error explaining why the review could not be completed (e.g., "File not found at specified path", "PR #123 does not exist in this repo") with suggested next steps.

## Guardrails

- **PHI:** This skill may encounter PHI in code being reviewed. If patient names, SSNs, DOBs, phone numbers, or insurance IDs are found hardcoded in code, flag as a CRITICAL security issue. Do NOT reproduce the PHI values in the review output — reference them by line number only.
- **Rate limits:** No external API calls. Local code analysis only.
- **Blast radius:** Review output is advisory only — no code is modified. Zero blast radius.
- **Cost:** Zero. No external API costs.
- **Permissions:** Requires read access to the files or repo being reviewed. No write access needed.

## Self-Verification

Before delivering output, the skill MUST verify:
- [ ] All 4 output sections are present (Critical, Important, Minor, Positive)
- [ ] Each finding includes a WHY explanation and specific code reference
- [ ] No PHI values are reproduced in the review output (line numbers only)
- [ ] MyBCAT conventions were checked: type hints, f-strings, logging (not print), parameterized SQL, proper error handling, no PHI logging
- [ ] Security review was performed: no hardcoded credentials, no SQL injection, no open security groups
- [ ] Review is actionable — vague feedback like "could be better" is replaced with specific suggestions

If any check fails, do NOT deliver output. Follow the Failure Path instead.

# Compound Engineering Primitives

Use this as Ankit's owned version of the Compound Engineering GO-now. It is a standards implant, not a third-party plugin adoption.

## Fire conditions

Apply for serious non-PHI code/repo/agentic engineering work when any of these are true:
- a task involves implementation across multiple files, repo changes, tests, PRs, deployment prep, or agent-generated code;
- a worker is about to claim fixed/done/complete/ready;
- a fresh-context review, Cross-Review QA, or Hermes Kanban review-required handoff is needed;
- a reusable lesson appears that should compound into a skill, runbook, solution note, or sanitized OB/Work Ledger capture.

Skip for tiny one-line edits, routine lookups, disposable scratch scripts, or any raw PHI/client-sensitive workflow. This skill does not authorize external sends, CRM/EHR/finance writes, deploys, merges, public uploads, or autonomous commit/push/PR loops.

## Core loop

Run: **Plan -> Work -> Review -> Compound -> Repeat**.

### 1. Plan

Before implementation, create or identify a durable yardstick:
- product/requirements contract separated from implementation plan;
- implementation units with stable IDs (`U1`, `U2`, ...);
- expected proof/test for each unit;
- acceptance criteria and explicit non-goals;
- the three decision-residue questions:
  1. What was the hardest decision made?
  2. What alternatives were rejected?
  3. What assumption is least confident?

If no yardstick exists for serious work, make one before changing code.

### 2. Work

Implement against unit IDs. Keep each proof attached to the unit it validates. Prefer the smallest safe diff that satisfies the yardstick.

### 3. Review

Run report-only review by default:
- fresh context when possible;
- reviewer findings cite the original plan/spec/unit, not the builder's narrative;
- reviewer/subagent outputs land in durable artifacts or run comments, not chat-only prose;
- user directives outrank reviewer best judgment; if a reviewer disagrees, it must flag rather than override;
- no auto-apply, merge, deploy, external send, or public upload from review alone.

### 4. Compound

Before saying done, classify the highest true state reached and attach evidence:
- local artifact only / tests passed / committed / pushed / PR opened / merged / deployed / live action taken / blocked / review-required;
- exact commands/tests/evidence;
- missing proof or skipped checks;
- changed files/artifacts;
- reusable lesson, if any.

If the lesson is reusable, update the smallest durable surface: skill patch, run-card line, solution note, or sanitized Work Ledger/OB capture. Do not capture raw secrets, PHI, client-sensitive details, raw IDs, or raw message bodies.

## Hard no's

- Do not raw-install the Every Compound Engineering plugin by default.
- Do not use `bunx @every-env/compound-plugin` unless version parity with the current repo/release is proven.
- Do not trust stale article/install claims without checking the repo/package state.
- Do not use side-effect-heavy flows such as autonomous commit/push/PR/CI as defaults.
- Do not use in PHI/client-sensitive contexts without explicit HIPAA/BAA/data-flow review.
- Do not upload proof/demo artifacts publicly without explicit user approval.

# Cross-Review QA

This skill makes cross-review the default QA gate for serious PRs and milestones. One model/context builds; a fresh QA worker reviews against the original plan/spec; the main agent fixes; the fresh reviewer re-checks. The reviewer must not inherit the builder's excuses.

When the QA worker is Claude Code, invoke it through `tmux-model-workers` in a named tmux session, never as a blind headless `claude -p` call. Codex CLI interactive QA may also use tmux; Codex `exec -s read-only` remains acceptable only when a one-shot read-only review is sufficient and the output is independently captured.

## Core rule

For every PR review or milestone review with maintainable, client-impacting, security/auth/data, production, or multi-file agent-built work:

1. Preserve the original yardstick: plan/spec/acceptance criteria, relevant ATLAS Index/SPINE, task card, and expected tests.
2. Spawn a **brand-new read-only QA worker**. Prefer a fresh Codex QA context for the existing mandatory Codex gate; when Claude Code is used for QA, launch it via `tmux-model-workers` in the repo/workspace and keep it read-only unless an explicit fix pass is authorized.
3. Give the QA worker the original yardstick + diff/artifacts + test evidence. Do **not** give it the builder's self-summary as the review source.
4. Require the QA worker to **do thought experiments**: simulate likely runtime states, variable values, branches, edge cases, and reproduction conditions against the diff/artifacts before judging PASS.
5. Require the QA worker to enumerate **only issues**, labeled `BLOCK`, `HIGH`, `MEDIUM`, or `LOW`, with file/section evidence and suggested fix direction.
6. Main agent fixes `BLOCK`/`HIGH` issues, reruns verification, and sends the updated packet back through a fresh QA re-review.
7. Stop only when no `BLOCK`/`HIGH` issues remain. Queue `MEDIUM`/`LOW` for human judgment unless they are cheap and clearly correct to fix.

Prefer **reciprocal cross-model QA** when an alternate primary coding surface is available: Claude-built or Claude-called work should be reviewed by Codex; Codex-built or Codex-called work should be reviewed by Claude Code; Hermes/Gemini work should route to the configured opposite reviewer. Fresh context remains mandatory, but for high-stakes/milestone work model diversity is now part of the expected gate. If the counterpart is unavailable, use the best independent fresh reviewer available, mark the gate degraded (for example `counterpart_unavailable=true`), and do not claim the reciprocal cross-model gate passed.

See `references/reciprocal-cross-model-qa.md` for the routing matrix, receipt expectations, and a proven recheck pattern from the project-lane normalization session.

## Trigger boundaries

Run this skill for:
- PR reviews before merge.
- Milestone reviews before claiming implementation/design complete.
- Agent-produced code or specs that will be maintained longer than a week.
- Auth, permissions, PHI/PII, tenant isolation, payments/finance, CRM/EHR, external sends, deploy, or production-write paths.
- A model has looped on a bug, finished suspiciously fast, or touched many files.
- Kanban/code tasks where the final state needs human review before `done`.

Skip or downshift for:
- Throwaway scripts, local prototypes, exploratory notebooks, or disposable one-off scrapes with no client/production/security impact.
- Purely conversational drafts with no implementation milestone.

## Security harness overlay

When QA touches auth, permissions, tenant isolation, secrets, PHI/PII, payments/finance, CRM/EHR, external sends, dependency/security changes, sandboxing, agent tool authority, or production-write paths, add a **read-only Defending Code Security Harness lane** to the fresh QA packet.

Use `defending-code-security-harness` as a reference/skill inside the fresh QA review. The reviewer must:

1. stay read-only/static unless the user explicitly approved sandboxed execution;
2. run the relevant mode: threat-model delta, static vulnerability scan, triage, or patch-review/re-attack plan;
3. anchor security claims to source paths/lines, not vibes;
4. output security issues as `SEC-QA-*` with `BLOCK/HIGH/MEDIUM/LOW` severity;
5. mark missing sandbox/preflight/test evidence as `BLOCK` or `HIGH` when it affects a required claim;
6. never include raw secrets, PHI, raw CRM/contact IDs, payment IDs, or client-sensitive bodies in the prompt/output.

This overlay is a QA lens, not an autonomous scanner. Do not let it create CI jobs, recurring scans, target execution, fuzzing, network probes, or security patches without separate approval and the normal gates.

## ATLAS / THROUGHLINE overlay

When a project ATLAS exists or an ATLAS hook fired, include the smallest relevant ATLAS Index/cluster in the QA packet and require inline THROUGHLINE:

- **Aim:** Does the output serve the SPINE/objective?
- **Ground:** Are claims, readiness labels, and completion claims tied to evidence, tests, or Evidenced nodes?
- **Thread:** Do the implementation/artifact pieces still connect through the typed edges/prereqs, or did the build drift?

ATLAS is not authorization. External sends, CRM/EHR/finance writes, deploys, merges, cron autonomy, and human-impacting labels still need their normal gates.

Severity definitions:
- `BLOCK`: Cannot honestly review/pass; missing yardstick, missing diff/artifacts, unsafe prompt contents, no test evidence for required gate, or likely high-blast-radius failure.
- `HIGH`: Must fix before merge/milestone completion; correctness, security, PHI/PII, tenant isolation, data loss, auth/permissions, broken tests, readiness-label mismatch, deploy/rollback gap.
- `MEDIUM`: Real defect or maintainability risk; human/product judgment may accept temporarily.
- `LOW`: Nits, naming, style, optional cleanup.

## Main-agent fix loop

After the QA worker returns:

1. Parse issues; do not bury `BLOCK`/`HIGH` under narrative.
2. Fix every `BLOCK`/`HIGH`, or explicitly block/escalate if a human decision is required.
3. Run the relevant tests/checks again and preserve real output.
4. Spawn a fresh QA re-review with the original yardstick, updated diff/artifacts, and new test evidence.
5. Repeat until `verdict` is `PASS` or `PASS_WITH_MEDIUM_LOW`.
6. Report final status with: reviews run, remaining MEDIUM/LOW decisions, tests run, and whether merge/completion is still gated.

Do not auto-merge, deploy, send externally, write CRM/EHR/finance records, or mark a human-impacting label solely because QA passed.

## Milestone review variant

For non-PR milestones, replace `git diff` with an artifact manifest:

- plan/spec/acceptance criteria
- produced docs/code/config/screenshots/reports
- test/eval outputs
- known skipped checks
- relevant ATLAS SPINE/cluster

The QA worker reviews whether the milestone claim is supported. If artifact status says "done" but tests/evidence are missing, that is at least `BLOCK` or `HIGH` depending on blast radius.

## Handoff format

When handing back to the user/board/reviewer:

```text
Cross-review QA status: PASS | PASS_WITH_MEDIUM_LOW | REQUEST_CHANGES | BLOCK
Fresh QA runs: <n> (<worker type: codex | claude-tmux | other>)
BLOCK/HIGH fixed: <count/list>
Remaining MEDIUM/LOW: <count/list or none>
Verification run: <commands + short real result>
Gate status: <merge/completion still gated? yes/no and why>
```

Keep summaries sanitized. Never include raw secrets, PHI, raw IDs, payment IDs, or raw message bodies.
# Compound Engineering addendum for repo-agent run cards

Use this compact checklist in serious non-PHI code/repo tasks.

## Required before work

- Plan/spec yardstick exists or is created.
- Product/requirements contract is separated from implementation plan.
- Work is split into stable unit IDs (`U1`, `U2`, ...).
- Each unit names expected proof/test.
- Decision residue is answered:
  - hardest decision made;
  - alternatives rejected;
  - least-confident assumption.

## Required during work

- Implement against unit IDs.
- Attach proof/test output to each completed unit.
- Prefer smallest safe diff; avoid speculative scaffolding.
- Keep PHI/client-sensitive data out unless an approved HIPAA-safe path exists.

## Required review gate

- Use report-only fresh-context review for serious tasks.
- Reviewers cite plan/spec/unit IDs, not only builder summaries.
- Findings land in durable artifacts, comments, or run logs.
- User directives outrank reviewer judgment; disagreements are flagged, not overridden.
- Review does not authorize merge/deploy/send/write/public upload.

## Required before done

- Behavior verification evidence is present.
- Highest true state is named: local artifact only, tests passed, committed, pushed, PR opened, merged, deployed, live action taken, blocked, or review-required.
- Changed files/artifacts and skipped checks are listed.
- Reusable lessons are captured as the smallest durable update: skill patch, runbook/solution note, or sanitized Work Ledger/OB entry.

## Third-party plugin guard

- Do not install Every's Compound Engineering plugin by default.
- Do not use npm/converter-backed installs unless package/release parity is proven.
- Use GitHub-pinned scratch-profile canaries only after proof slots are satisfied.
- Never use raw plugin flows in PHI/client-sensitive contexts without explicit review.

# Project Room Gate


## Bundled resources

<!-- skill-auditor-resource-index -->
- `references/cross-surface-implantation-2026-05-22.md`

## Purpose

Use this skill to prevent polished synthesis from laundering stale, duplicated, weak, or conflicting sources. It implements the Project Room Gate v0.1 pattern for Ankit/MyBCAT: build and review the room before drafting any high-stakes multi-source artifact.

Canonical source: OB_mybcat. Before applying this skill to durable work, search OB_mybcat for topic `project-room-gate` and load the newest thought titled `Project Room Gate v*`. If OB_mybcat is unavailable, use this local v0.1 fallback and say so.

## When to Use

Use for any synthesis, memo, deck, model review, strategic recommendation, workflow spec, diligence packet, or operating decision where one or more are true:

- 3 or more source inputs are involved.
- Output is external-facing, investor/client/team-facing, or likely to travel beyond the live conversation.
- Output affects financial, security, strategy, personnel, compliance, or agent-autonomy decisions.
- Sources may be stale, duplicated, superseded, contradictory, or spread across OB_mybcat, files, transcripts, email, MCP queries, Drive, Git, CRM, spreadsheets, or meetings.
- User mentions project room, build the room, source inventory, duplicate log, missing context, authority ranking, draftable, room state, room refresh, or Nate's May 22 room idea.

Do not use for low-stakes conversational replies, single-source summaries, retrieval-only lookups, or drafts explicitly labeled as exploratory/internal-only.

## Core Rule

No high-stakes multi-source deliverable may be drafted until its Project Room is reviewed and marked `draftable`.

If there is no room, no reviewed inventory, stale room state, unresolved blocking missing context, or factual claims without source IDs, refuse to draft. Offer to build or refresh the room instead.

Allowed exception: produce an explicitly labeled `unroomed / internal-only / not for external use` sketch, with missing-context and source-risk caveats at the top.

## Local Automation: roomctl

When `/home/ankit114/.mybcat/bin/roomctl` exists, use it as the deterministic local control surface before high-stakes synthesis. It stores Room Lite / Project Room state under `/home/ankit114/.mybcat/project_rooms` by default. Use `MYBCAT_ROOMCTL_HOME` only for tests or isolated runs.

Default commands:

```bash
roomctl preflight "<task>" --project "<project>" --source-count <n> --external-facing --strategy --json
roomctl create "<project>" --owner "Ankit" --source-root /path/to/source --json
roomctl detect --root /mnt/d_drive/repos --json
roomctl stale-scan --json
roomctl set-state "<project>" draftable --note "source inventory reviewed" --json
roomctl add-source "<project>" /path/or/url --type file --current-status current --allowed-use numbers --json
roomctl add-gap "<project>" "Missing current assumptions" --needed-before draft --owner Ankit --json
```

Preflight return code discipline:

- `0`: synthesis allowed or room not required.
- `2`: Project Room required but blocked. Do not draft; build/refresh/review the room or label output unroomed/internal-only.
- `1`: tool/runtime error. Fail closed and do not draft.

Use Room Lite for broad project coverage: create/detect records for meaningful projects without forcing full inventory. Escalate to Full Project Room only when preflight says room is required.

## Room State Machine

- `empty`: room exists but no source inventory has been built.
- `inventory_built`: sources are listed but not reviewed.
- `inventory_review_required`: authority calls, conflicts, or gaps require human/project-owner review.
- `inventory_reviewed`: source map was accepted.
- `draftable`: synthesis is allowed.
- `stale`: new source, elapsed cadence, or changed premise invalidated the room.
- `blocked`: missing context prevents useful or safe synthesis.

State transitions must be explicit. A room becomes `stale` when new material arrives, a project premise changes, or the refresh cadence expires.

## Four Required Artifacts

### 1. Source Inventory

For each source, capture:

- `source_id`
- `project_room_id`
- `source_type`: file, URL, transcript, email, MCP query, OB thought, spreadsheet, CRM export, meeting note, other
- `location_ref`: path, URL, query ref, thought id, or durable pointer, never raw secrets
- `captured_at`
- `source_owner`
- `authority_rank`
- `current_status`: current, superseded, background, rejected, unknown
- `allowed_use`: numbers, rationale, quotes, context, task list, not usable, other
- `sensitive_data_class`
- `review_status`: unreviewed, proposed, reviewed, rejected
- `notes`

### 2. Duplicate and Version Log

Track exact duplicates, likely duplicates, version families, canonical version chosen, superseded versions, conflicts, and rationale for which source wins.

### 3. Missing-Context List

For each gap, capture:

- `gap`
- `why_it_matters`
- `blocked_claims`
- `risk_if_ignored`
- `owner`
- `needed_before`: draft, send, publish, decision, build
- `status`: open, accepted-risk, resolved, not-needed

A claim blocked by an open gap cannot appear in the draft as fact.

### 4. Working Brief

Summarize:

- what the room supports
- what it does not support
- current conflicts
- draftable claims
- non-draftable claims
- open decisions
- recommended next action

## Authority Ranking Defaults

Use source authority for source material, not for Ankit's personal thinking tiers. Suggested default order, adapted per room:

1. Signed/current source of record, approved plan, executed agreement, current system export.
2. Current project-owner decision or reviewed OB_mybcat canonical thought.
3. Current working doc or latest reviewed model.
4. Meeting transcript/email that explains context but does not override source-of-record numbers.
5. Older decks, stale docs, unreviewed notes, and inferred summaries as background only.

High-stakes authority ranking is a human/project-owner gate. The agent may propose ranking, but should not silently finalize it.

## Workflow

1. Identify whether the task triggers Project Room Gate.
2. Search OB_mybcat for the newest Project Room Gate version and any existing room decision for the project.
3. If no room exists, create a proposed room with the four artifacts.
4. Inventory sources by pointer/reference. Do not copy raw sensitive data into durable surfaces.
5. Propose duplicate/version families and authority ranking.
6. Produce missing-context list before synthesis.
7. Ask the project owner to review authority ranking and blocking gaps when stakes require it.
8. Set room state.
9. Draft only if state is `draftable`.
10. Reviewer audits that factual claims cite source IDs and do not exceed room support.

## Reviewer Gate

Before approving any draft, check:

- Does a Project Room exist for this artifact?
- Is the source inventory reviewed?
- Is room state `draftable`?
- Is the room not stale?
- Are conflicts declared with a winning source?
- Are blocking missing-context items resolved or accepted by an owner?
- Do factual claims cite source IDs?
- Are unsupported claims removed or labeled as hypotheses?

If any answer fails, halt the draft and route to room build/refresh.

## Relation to AAC v1.1

Project Room Gate is not a new AAC primitive. Treat it as a workflow element under AAC v1.1:

- BOUNDED: finite room states and source status values.
- GROUNDED: claim-to-source IDs required.
- GATED: no draft unless room is draftable.
- OBSERVED: track room state, stale events, missing-context count, draft failures, and reviewer halts.
- GOVERNED: stale-room kill switch and owner review for authority ranking.

For AI workflow readiness, require task-specific executed proof and applicable workflow-native gates. Do not declare production-ready based only on Project Room Gate. AAC is manual-only and is added only when Ankit explicitly requests it.

## OB_mybcat Capture Rules

Capture to OB_mybcat:

- canonical Project Room Gate policy and version updates
- room-level decisions and accepted authority ranking
- accepted exceptions/residue
- reusable failure modes discovered by Reviewer

Do not capture raw source dumps, secrets, PHI/PII, or every intermediate note. Use durable pointers and minimized summaries.

## First Pilot

Default first pilot is the rollup financial model room. Use it to prove the gate catches at least one stale source, source conflict, missing context item, or unsupported claim before promoting broadly.

## Common Pitfalls

1. Building a slash command before the room state contract. Interface is secondary; state and refusal are the value.
2. Treating OB_mybcat as the raw source database. OB_mybcat stores governing decisions and minimized summaries, not every source byte.
3. Letting a beautiful draft bypass source review. Reviewer must check room state before prose quality.
4. Applying the gate to every small answer. Use it for durable/high-stakes synthesis, not normal conversation.
5. Finalizing authority ranking autonomously on high-stakes work. Propose it, then get owner review.
6. Forgetting staleness. A previously valid room can become invalid when new sources arrive or cadence expires.

## Verification Checklist

- [ ] Latest OB_mybcat Project Room Gate version retrieved or fallback declared.
- [ ] Trigger decision made: room required vs not required.
- [ ] Four artifacts exist or absence is explicitly blocking.
- [ ] Room state is one of the allowed values.
- [ ] Source authority and missing context reviewed for high-stakes work.
- [ ] Drafting refused unless room is `draftable` or output is labeled unroomed/internal-only.
- [ ] Durable room decisions captured to OB_mybcat with minimized source references.

# threat-model

A threat model answers **"what could go wrong with this system, who would do
it, and what should we do about it?"** independently of whether any specific
bug has been found yet. It is the map; vulnerability discovery is the metal
detector. A good threat model tells the pipeline where to look and tells triage
which findings matter.

**Litmus test:** If patching one line of code makes an entry disappear, it was
a vulnerability, not a threat. A threat ("attacker achieves RCE via untrusted
media parsing") still stands after every known bug is fixed; a vulnerability
("`dr_wav.h:412` doesn't bounds-check `chunk_size`") does not. This skill
produces threats. Vulnerabilities appear only as **evidence** that raises a
threat's likelihood score.

**Invocation:** `/threat-model [bootstrap-then-interview|bootstrap|interview] <target-dir> [flags]`

## Step 0 — Safety preamble (always runs first)

This skill performs **static analysis only**. It reads source, git history,
and any vulnerability reports the user supplies, and writes a single output
file (`<target-dir>/THREAT_MODEL.md`). It does not build, execute, fuzz, or
modify the target, and does not make network requests against the target's
infrastructure.

Before proceeding, confirm and state in your first response:

1. The target directory exists and is a local checkout you can read.
2. You will not execute any code from the target directory.
3. If `--vulns` points at a URL or you are asked to "fetch CVEs", you will
   query only public advisory databases (NVD, GitHub Security Advisories, the
   project's own issue tracker) and never the target's live deployment.

If the user asks you to validate a threat by running an exploit, decline and
point them at the `vuln-pipeline` (README Step 2) instead.

## Step 1 — Route to a mode

Parse `$ARGUMENTS`:

| First token | Route to |
|---|---|
| `interview` | Read `interview.md` in this directory and follow it. |
| `bootstrap` | Read `bootstrap.md` in this directory and follow it. |
| `bootstrap-then-interview` | Bootstrap first, then interview seeded from the draft. See below. |

so downstream consumers (pipeline `recon`/`judge`, verifier agents) do not need
to know which mode produced it.

| | `interview` | `bootstrap` |
|---|---|---|
| **Needs** | An application owner present in the session | A local checkout; optionally past vulns |
| **Method** | Four-question framework: conversational walk through *what are we working on → what can go wrong → what are we going to do about it → did we do a good job* | Five stages: parallel research swarm → synthesize sections 1-3 + vuln table → generalize vulns into threat classes → STRIDE gap-fill → emit |
| **Best for** | New systems, design reviews, systems where the risk lives in business logic the code doesn't show | Inherited systems, third-party code, OSS dependencies, anything with a CVE history |
| **Provenance tag** | `interview` | `bootstrap` |

**Context durability.** Interview mode is multi-turn; tool results from early
reads may be evicted before you need them. To stay resilient:

- Do **not** read `interview.md` or `bootstrap.md` in full up front. Read the
  mode file (or the relevant section of it) **at the point you need it**, one
  question or stage at a time.
- If a re-read via the Read tool is refused as "file unchanged", the prior
  result was evicted; reload with `cat <path>` via Bash instead.

**Interview backbone** (so you can proceed even if `interview.md` is
unavailable mid-session):

| Q | Question | Fills schema sections |
|---|---|---|
| Q1 | What are we working on? | section 1 context, section 2 assets, section 3 entry points |
| Q2 | What can go wrong? | section 4 threat rows (id, threat, actor, surface, asset) |
| Q3 | What are we going to do about it? | section 4 impact/likelihood/status/controls; section 5 deprioritized; section 8 recommended mitigations |
| Q4 | Did we do a good job? | validate ranking, coverage check, section 6 open questions |

### `bootstrap-then-interview` mode

When the owner is available *and* the codebase is checked out, this is the
recommended path: the owner's time goes to refining a code-grounded draft
instead of describing the system from scratch.

1. Tell the owner: "I'll read the code first and come back with a draft
   (about 5-10 min), then we'll walk it together. Want that, or would you
   rather start cold?" Only proceed if they opt in; otherwise fall back to
   `interview.md`.
2. Read `bootstrap.md` and follow it end-to-end. Write
   `<target-dir>/THREAT_MODEL.md`.
3. Immediately continue into interview mode: read `interview.md` and follow
   it with `--seed <target-dir>/THREAT_MODEL.md` in effect. The section 6 open
   questions from bootstrap become your Q1-Q4 prompts; the owner confirms,
   corrects, and adds rather than starting from nothing.
4. Overwrite `<target-dir>/THREAT_MODEL.md` with the refined model. Set
   provenance `mode: bootstrap-then-interview`.

The same flow is available manually: run `bootstrap` first, then
`interview --seed <THREAT_MODEL.md>` in a later session.

## Step 2 — Shared output contract

All modes MUST emit `<target-dir>/THREAT_MODEL.md` conforming to `schema.md`
in this directory. **Read `schema.md` immediately before you write the file**,
not at routing time; in interview mode the gap between routing and emit can be
many turns, and an early read will be evicted before it's used.

After writing the file, print to the user:

1. The path to `THREAT_MODEL.md`.
2. The top 5 threats by likelihood × impact (id, one-line description, L×I).
3. For `bootstrap`: any open questions the code could not answer (these seed a
   later `interview` pass).
4. For `interview`: any owner statements that could not be verified in code
   (these seed follow-up code review).

# Security considerations

> **TL;DR:** The autonomous pipeline executes target code. Run it via
> `bin/vp-sandboxed`, which confines every agent in a gVisor container with
> egress restricted to the API. Never mount credential-bearing paths into
> anything an agent can reach. The interactive skills `/threat-model`,
> `/vuln-scan`, `/triage`, and `/quickstart` only read and write files and
> therefore don't need a sandbox. `/customize` also edits pipeline source and 
> may run validation commands, so you should review its proposed plan before 
> approving.

## Why the sandbox is necessary

Frontier models are increasingly good at finding creative paths around
restrictions. This is what makes them effective vulnerability hunters. 
However, it also makes them capable of taking unexpected actions against 
their own execution environments. See the
[blog post's sandbox section](blog-post.md#2-sandbox-run-agents-safely-and-verify-exploitability) for
examples of where teams have seen this in the wild.

The lesson we've learned from our work is that models will use whatever
capabilities they actually have access to, not necessarily just what you
tell them they have. For that reason, **constraints must be enforced in code,
not in prompts.**

This repo does that for you. Every agent runs inside a gVisor container
with network egress limited to the Claude API (as described in 
[agent-sandbox.md](agent-sandbox.md)). Agent-spawning subcommands refuse to
start outside that sandbox unless you explicitly pass `--dangerously-no-sandbox`.

## Rules for running autonomous agents

- Launch the pipeline using `bin/vp-sandboxed` which verifies the sandbox
  is set up before starting any agents.
- Don't run autonomous agents in plain Docker (with `runc`). Ordinary 
  containers share your host's kernel, so a kernel bug triggered by the
  target inside the container can compromise your host.
- Don't run containers with `--privileged` or with host networking.
- Match the level of isolation to the task. A plain container is fine for
  an agent that can only read code, while something with stronger isolation
  (e.g., gVisor, Kata Container, Firecracker microVM) should be used for
  running the target.
- Never mount credential-bearing paths (e.g., `~/.aws`, `.env`) into the
  agent's environment.
- Don't connect agents to MCP servers or tools that can write to the outside 
  world (prod infrastructure, email, cloud storage).
- If you're driving the pipeline interactively from Claude Code, rely on the
  auto-mode permission classifier and have a human approve any action that
  reaches outside the repo.

> For a full treatment of isolation options, credential proxying, and filesystem 
> hardening, see Anthropic's guide on [securely deploying AI agents](https://platform.claude.com/docs/en/agent-sdk/secure-deployment).

## Separating setup and attack phases

The general pattern (described in the
[blog post](blog-post.md#2-sandbox-run-agents-safely-and-verify-exploitability))
is to do everything that needs the internet first (pull dependencies, install
tools, etc.), freeze the result, and give the attack phase no egress route
except to the model API.

In this repo, that split looks like:

1. Setup: Building the target image - `docker build` pulls dependencies
   and compiles the target with normal network access. The agents then run
   against that image on the `vp-internal` network, where the only way out 
   is the allowlist proxy (`api.anthropic.com:443` by default).
2. Freeze: the image is the snapshot. Base images, commit SHAs, and dependency 
   versions are pinned in the Dockerfile so every run uses the same bits.

See [agent-sandbox.md](agent-sandbox.md) for more details on this setup.

## Prompt injection

To minimize the risk of prompt injection attacks, don't give the agents 
untrusted skills, plugins, or MCP servers from the internet.

The pipeline's own agents also read target-derived data: ASAN traces (which
contain function names and file paths from the target's symbol table),
exploitability reports, and build/test output. A malicious target author
could in principle embed instructions in those strings. The find and report
agents have limited blast radius. They run inside a gVisor container on an
internal network with egress restricted to the API, and they only produce files
that you read. The **patch agent** is the higher-stakes case. Its output is
a diff you may apply to a real codebase. The pipeline wraps target-derived
text in the patch prompt in `<untrusted_data>` blocks with a per-call random 
id and instructs the agent to treat it as only data (not instructions). However,
these measures are a mitigation, not a guarantee. Review every generated diff
before upstreaming. See [patching.md](patching.md#reviewing-generated-patches) 
for what to look for.

    38	date, given the three constraints. It spans TWO layers and must say exactly what each does:
    39	- The MODEL (extraction on n_ask / n_negotiate etc): the smallest, safest transformation
    40	  that cannot invent a weekday. For example: copy the patient's most explicit date token
    41	  verbatim; only emit a weekday word if the patient literally said that weekday; never
    42	  derive one from a date or from "tomorrow".
    43	- The GATEWAY resolver (bland_gateway.py resolve_relative_date): what it must additionally
    44	  accept so the model can pass patient-literal phrasing through -- for example strip an
    45	  ordinal suffix ("28th" -> "28"), accept "july 28th", and a rule for a compound carrying
    46	  two date cues (prefer the explicit month-day; define conflict handling).
    47	Also state where "tomorrow" is handled (the gateway already does it) and the rule when the
    48	patient gives BOTH a relative word and an explicit date that agree, and when they disagree.
    49	Note the Monday-anchored week fix already deployed; do not undo it.

    79	def load_consumer_credential_set(raw: str) -> tuple[list[dict], bool]:
    80	    """Parse all consumer credentials atomically without logging their values."""
    81	    if not isinstance(raw, str) or not raw.strip():
    82	        return [], False
    83	    try:
    84	        document = json.loads(raw)
    85	    except (TypeError, json.JSONDecodeError):
    86	        return [], True
    87	    if (
    88	        not isinstance(document, dict)
    89	        or set(document) != {"version", "consumers"}
    90	        or not isinstance(document["version"], int)
    91	        or isinstance(document["version"], bool)
    92	        or not isinstance(document["consumers"], list)
    93	    ):
    94	        return [], True
    95	
    96	    consumers = []
    97	    consumer_ids = set()
    98	    tokens = []
    99	    for record in document["consumers"]:
   100	        if not isinstance(record, dict) or set(record) != CONSUMER_CREDENTIAL_FIELDS:
   101	            return [], True
   102	        if not all(
   103	            isinstance(record[key], str) and record[key].strip()
   104	            for key in ("consumer_id", "token", "tenant", "principal")
   105	        ):
   106	            return [], True
   107	        if not isinstance(record["enabled"], bool):
   108	            return [], True
   109	        if (
   110	            not isinstance(record["routes"], list)
   111	            or not all(isinstance(route, str) and route.strip() for route in record["routes"])
   112	        ):
   113	            return [], True
   114	        if (
   115	            not isinstance(record["rate_per_minute"], int)
   116	            or isinstance(record["rate_per_minute"], bool)
   117	        ):
   118	            return [], True
   119	
   120	        consumer_id = record["consumer_id"].strip()
   121	        token = record["token"].strip()
   122	        if consumer_id in consumer_ids or any(
   123	            hmac.compare_digest(token, existing_token) for existing_token in tokens
   124	        ):
   125	            return [], True
   126	        consumer_ids.add(consumer_id)
   127	        tokens.append(token)
   128	        consumers.append(
   129	            {
   130	                **record,
   131	                "consumer_id": consumer_id,
   132	                "token": token,
   133	                "tenant": record["tenant"].strip(),
   134	                "principal": record["principal"].strip(),
   135	                "routes": [route.strip() for route in record["routes"]],
   136	            }
   137	        )

   310	def normalize_phone(val) -> str:

   312	    # E.164 (+1XXXXXXXXXX), which is what Bland's {{from}} sends — that mismatch

   314	    # to the bare 10 digits; pass anything else through unchanged.

   348	def _fmt(dt):
   349	    # Zero-padded hour (%I, not %-I): the EyeCloud scheduler CLI rejects
   350	    # unpadded times ('bad --start: unrecognized scheduler time "07/14/2026
   351	    # 4:00 pm"', proven live 2026-07-14 on the urgent double-book lane), and
   352	    # the CLI's own availability output is padded, so padded is canonical.
   353	    return dt.strftime("%m/%d/%Y %I:%M %p").lower()

   370	def hours_state(store: str, now) -> dict:
   371	    cfg = _hours_cfg()
   372	    store_cfg = (cfg.get("stores") or {}).get(str(store).strip().lower())
   373	    if not store_cfg:
   374	        raise ValueError("unknown store")
   375	    buf = int(cfg.get("about_to_close_minutes", 30))
   376	    win = _day_window(cfg, store_cfg, now)
   377	    state, closes_at = "after_hours", ""
   378	    if win and win[0] <= now < win[1]:
   379	        closes_at = _fmt(win[1])
   380	        state = "about_to_close" if (win[1] - now).total_seconds() <= buf * 60 else "open"
   381	    probe = now
   382	    if not (win and now < win[0]):
   383	        probe = probe + timedelta(days=1)
   384	    for _ in range(14):
   385	        w = _day_window(cfg, store_cfg, probe.replace(hour=0, minute=0))
   386	        if w:
   387	            first_am = w[0]
   388	            break
   389	        probe = probe + timedelta(days=1)
   390	    else:
   391	        raise ValueError("no open day within 14 days")
   392	    return {"state": state, "closes_at": closes_at, "first_am_start": _fmt(first_am)}

   395	def _next_open_dt(cfg, store_cfg, now):
   396	    probe = now
   397	    if not (_day_window(cfg, store_cfg, now) and now < _day_window(cfg, store_cfg, now)[0]):
   398	        probe = probe + timedelta(days=1)
   399	    for _ in range(14):
   400	        w = _day_window(cfg, store_cfg, probe.replace(hour=0, minute=0))
   401	        if w:
   402	            return w[0]
   403	        probe = probe + timedelta(days=1)
   404	    raise ValueError("no open day within 14 days")

   413	def urgent_window(store: str, slot_mode: str, now) -> dict:
   414	    """Resolve the concrete availability window + double-book target for an urgent
   415	    booking. same_day only holds while the office is open/about-to-close; anything
   416	    else (or an after-hours same_day request) falls back to first_am. Pure function
   417	    of (store, mode, now) so the pathway never does date math."""
   418	    cfg = _hours_cfg()
   419	    store_cfg = (cfg.get("stores") or {}).get(str(store).strip().lower())
   420	    if not store_cfg:
   421	        raise ValueError("unknown store")
   422	    mode = str(slot_mode).strip().lower()
   423	    win = _day_window(cfg, store_cfg, now)
   424	    open_now = bool(win and win[0] <= now < win[1])
   425	    if mode == "same_day" and open_now:
   426	        book_start = _next_boundary(now)
   427	        last = win[1] - timedelta(minutes=30)
   428	        if book_start > last:
   429	            book_start = last
   430	        return {"mode": "same_day", "avail_from": _fmt(now), "avail_to": _fmt(win[1]),
   431	                "book_start": _fmt(book_start), "book_end": _fmt(book_start + timedelta(minutes=30))}
   432	    first_am = _next_open_dt(cfg, store_cfg, now)
   433	    return {"mode": "first_am", "avail_from": _fmt(first_am),
   434	            "avail_to": _fmt(first_am + timedelta(hours=4)),
   435	            "book_start": _fmt(first_am), "book_end": _fmt(first_am + timedelta(minutes=30))}

   440	    appointment id is actually present in a re-read of the patient's appointment

   475	def resolve_relative_date(raw) -> str | None:
   476	    # Dates reach us from LLM-extracted variables; the CLI only accepts
   477	    # MM/DD/YYYY or YYYY-MM-DD, so anything else must be resolved here, not
   478	    # left for the model to format (live failure 2026-07-21: "Friday" reached
   479	    # the CLI verbatim -> 409). Bare/this/next weekday means the next future
   480	    # occurrence (Eastern, never today). "Next week" means the next calendar
   481	    # week's Monday. English and Chinese weekday-plus-week phrases use that
   482	    # weekday in the next/second-next Monday-anchored calendar week.
   483	    # Explicit-year dates pass through unmodified; rewriting a year the caller
   484	    # stated would surprise them.
   485	    from datetime import datetime, timedelta
   486	
   487	    today = _eastern_today().date()
   488	    t = re.sub(r"[.,!?]", "", str(raw or "").strip().lower())
   489	    t = re.sub(r"\s+", " ", t)
   490	    if not t:
   491	        return None

   494	        return day.strftime("%m/%d/%Y")

   498	        return today + timedelta(days=ahead)

   504	    simple_days = {
   505	        "today": 0, "tomorrow": 1, "tmrw": 1, "tmr": 1,
   506	        "day after tomorrow": 2,
   507	        "今天": 0, "明天": 1, "后天": 2, "大后天": 3,
   508	    }
   509	    if t in simple_days:
   510	        return emit(today + timedelta(days=simple_days[t]))
   511	
   512	    if t in ("next week", "下周"):
   513	        return emit(calendar_weekday(0, 1))
   514	
   515	    # "Coming weekend" follows the existing bare-weekday rule: it is always
   516	    # the next future Saturday, even when today is Saturday.
   517	    if t in ("weekend", "this weekend", "周末", "这周末"):
   518	        return emit(next_weekday(5))
   519	    if t == "next weekend":
   520	        return emit(next_weekday(5) + timedelta(days=7))
   521	    if t == "下周末":
   522	        return emit(calendar_weekday(5, 1))
   523	
   524	    match = re.fullmatch(r"(?:in )?(\d+) days(?: from now)?", t)
   525	    if not match:
   526	        match = re.fullmatch(r"(\d+) days from now", t)
   527	    if match:
   528	        return emit(today + timedelta(days=int(match.group(1))))
   529	
   530	    number_words = {
   531	        "one": 1, "two": 2, "three": 3, "four": 4, "five": 5,
   532	        "six": 6, "seven": 7, "eight": 8, "nine": 9, "ten": 10,
   533	        "couple": 2,
   534	    }
   535	    match = re.fullmatch(r"in (?:a|a (couple)|(\d+|one|two|three|four|five|six|seven|eight|nine|ten|couple)) weeks?", t)
   536	    if match:
   537	        count_text = match.group(1) or match.group(2)
   538	        count = 1 if count_text is None else number_words.get(
   539	            count_text, int(count_text) if count_text.isdigit() else None
   540	        )
   541	        return emit(today + timedelta(days=7 * count))
   542	    match = re.fullmatch(r"(\d+) weeks (?:from now|out)", t)
   543	    if match:
   544	        return emit(today + timedelta(days=7 * int(match.group(1))))
   545	
   546	    zh_numbers = {
   547	        "一": 1, "二": 2, "两": 2, "三": 3, "四": 4, "五": 5,
   548	        "六": 6, "七": 7, "八": 8, "九": 9, "十": 10,
   549	    }
   550	    match = re.fullmatch(r"(\d+|[一二两三四五六七八九十])天后", t)
   551	    if match:
   552	        count = int(match.group(1)) if match.group(1).isdigit() else zh_numbers[match.group(1)]
   553	        return emit(today + timedelta(days=count))
   554	    match = re.fullmatch(r"(\d+|[一二两三四五六七八九十])(?:周|个星期)后", t)
   555	    if match:
   556	        count = int(match.group(1)) if match.group(1).isdigit() else zh_numbers[match.group(1)]
   557	        return emit(today + timedelta(days=7 * count))
   558	
   559	    zh_weekdays = {"一": 0, "二": 1, "三": 2, "四": 3, "五": 4, "六": 5, "日": 6, "天": 6}
   560	    match = re.fullmatch(r"(下下|下|这|本)?(?:周|星期|礼拜)([一二三四五六日天])", t)
   561	    if match:
   562	        prefix, day_text = match.groups()
   563	        weekday = zh_weekdays[day_text]
   564	        if prefix == "下":
   565	            return emit(calendar_weekday(weekday, 1))
   566	        if prefix == "下下":
   567	            return emit(calendar_weekday(weekday, 2))
   568	        return emit(next_weekday(weekday))
   569	
   570	    weekday_pattern = "|".join(sorted(_WEEKDAYS, key=len, reverse=True))
   571	    match = re.fullmatch(rf"(?:day after next|the day after) ({weekday_pattern})", t)
   572	    if match:
   573	        return emit(next_weekday(_WEEKDAYS[match.group(1)]) + timedelta(days=1))
   574	    match = re.fullmatch(rf"({weekday_pattern}) after next", t)
   575	    if match:
   576	        return emit(calendar_weekday(_WEEKDAYS[match.group(1)], 2))
   577	    match = re.fullmatch(rf"(?:a week from ({weekday_pattern})|({weekday_pattern}) next week)", t)
   578	    if match:
   579	        weekday_text = match.group(1) or match.group(2)
   580	        return emit(calendar_weekday(_WEEKDAYS[weekday_text], 1))
   581	
   582	    weekday_text = re.sub(r"^(this|next|on|coming)\s+", "", t)
   583	    if weekday_text in _WEEKDAYS:
   584	        return emit(next_weekday(_WEEKDAYS[weekday_text]))
   585	    for fmt in ("%m/%d/%Y", "%Y-%m-%d", "%m-%d-%Y", "%B %d %Y", "%b %d %Y"):
   586	        try:
   587	            return datetime.strptime(t, fmt).date().strftime("%m/%d/%Y")
   588	        except ValueError:
   589	            continue
   590	    # Yearless dates: the year is ours to pick, so a day that already passed
   591	    # this year means the next occurrence.
   592	    for fmt in ("%m/%d", "%B %d", "%b %d"):
   593	        try:
   594	            d = datetime.strptime(t, fmt).date().replace(year=today.year)
   595	        except ValueError:
   596	            continue
   597	        if d < today:
   598	            try:
   599	                d = d.replace(year=d.year + 1)
   600	            except ValueError:  # Feb 29
   601	                d = d.replace(month=2, day=28, year=d.year + 1)
   602	        return d.strftime("%m/%d/%Y")
   603	    return None

   606	def clamp_availability_range(body: dict) -> None:
   607	    # first_available=1 replaces from/to with tomorrow..+6 days (Eastern) —
   608	    # closed days simply return no slots, so no business-day logic is needed.
   609	    # Otherwise from/to go through resolve_relative_date; bad/inverted "to"
   610	    # collapses to same-day; spans are capped at 14 days.
   611	    from datetime import datetime, timedelta
   612	
   613	    first = str(body.pop("first_available", "")).strip().lower()
   614	    if first in ("1", "true", "yes"):
   615	        start = _eastern_today() + timedelta(days=1)
   616	        body["from"] = start.strftime("%m/%d/%Y")
   617	        body["to"] = (start + timedelta(days=6)).strftime("%m/%d/%Y")
   618	        return
   619	
   620	    def parse(v):
   621	        try:
   622	            return datetime.strptime(str(v).strip(), "%m/%d/%Y")
   623	        except ValueError:
   624	            return None
   625	
   626	    resolved = resolve_relative_date(body.get("from"))
   627	    if resolved is None:
   628	        return
   629	    body["from"] = resolved
   630	    frm = parse(resolved)
   631	    to_resolved = resolve_relative_date(body.get("to"))
   632	    to = parse(to_resolved) if to_resolved else None
   633	    if to is None or to < frm:
   634	        to = frm
   635	    if (to - frm).days > 13:
   636	        to = frm + timedelta(days=13)
   637	    body["to"] = to.strftime("%m/%d/%Y")

   640	def sanitize_patient_search(body: dict):
   641	    # Identity safety (live chat-test finding 2026-07-01): an unresolved Bland
   642	    # variable like "{{from}}" reached EyeCloud as a phone filter, EyeCloud
   643	    # ignored it, and the search returned an unfiltered patient list; a
   644	    # DOB-only follow-up then matched the WRONG real patient. Rules:
   645	    #   - a phone that doesn't normalize to 10 digits is dropped
   646	    #   - dob without last/first/phone is never searched (wrong-person risk)
   647	    #   - if nothing usable remains, short-circuit to a clean 0-match so the
   648	    #     pathway falls into its ask-for-last-name-and-DOB lane
   649	    phone = str(body.get("phone", "")).strip()
   650	    if phone and not re.fullmatch(r"\d{10}", normalize_phone(phone)):
   651	        body.pop("phone", None)
   652	    has = {k: str(body.get(k, "")).strip() for k in ("last", "first", "phone", "dob")}
   653	    if has["dob"] and not (has["last"] or has["phone"]):
   654	        body.pop("dob", None)
   655	        has["dob"] = ""
   656	    if not (has["last"] or has["phone"]):
   657	        return {"count": 0, "capped": False, "patients": []}
   658	    return None

   731	    """Validate and idempotently record one SMS suppression."""
   732	    global _sms_suppression_client
   733	
   734	    for field in ("phone_e164", "reason", "source"):
   735	        if field not in body:

   740	    source = body["source"]

   751	    if boto3 is None:
   752	        raise SuppressionStoreError("suppression_store_unavailable")

   755	        "+00:00", "Z"

   905	class ConsumerResolution(NamedTuple):
   906	    consumer: dict | None
   907	    outcome: str
   908	
   909	
   910	def resolve_consumer(headers, method: str, path: str) -> ConsumerResolution:
   911	    """Resolve a deployment-bound consumer solely from its bearer token."""
   912	    auth = headers.get("Authorization", "")
   913	    if not auth.startswith("Bearer "):
   914	        return ConsumerResolution(None, "unknown_token")
   915	    presented_token = auth[7:].strip()
   916	    matched = None
   917	    for record in CONSUMER_CREDENTIALS:
   918	        if hmac.compare_digest(presented_token, record["token"]):
   919	            matched = record
   920	            break
   921	    if matched is None:
   922	        return ConsumerResolution(None, "unknown_token")
   923	    if matched["tenant"] != TENANT_ID or matched["principal"] != READ_PRINCIPAL:
   924	        return ConsumerResolution(matched, "unknown_token")
   925	    if not matched["enabled"]:
   926	        return ConsumerResolution(matched, "disabled")
   927	    route = f"{method.upper()} {path}"
   928	    wildcard_all = matched["routes"][-1:] == ["*"]
   929	    if not wildcard_all and route not in matched["routes"]:
   930	        return ConsumerResolution(matched, "forbidden_scope")
   931	    return ConsumerResolution(matched, "ok")
   932

   934	def resolve_request_auth(headers, method: str, path: str) -> ConsumerResolution:
   935	    """Resolve consumer auth, falling back to the legacy bearer only when safe."""
   936	    resolution = resolve_consumer(headers, method, path)
   937	    if resolution.outcome == "ok":
   938	        return resolution
   939	    if (
   940	        resolution.consumer is None
   941	        and resolution.outcome == "unknown_token"
   942	        and not CONSUMER_CREDENTIALS_LOAD_FAILED
   943	        and CONSUMER_ACCEPT_LEGACY
   944	        and authed(headers)
   945	    ):
   946	        return ConsumerResolution(None, "ok")
   947	    return resolution

  1044	def deliver_message(body: dict) -> dict:
  1045	    """Email a captured callback message to the practice inbox. Raises on refusal
  1046	    (400/503-worthy) so do_POST maps it to a status. No PHI is logged here."""
  1047	    if not CALLBACK_INBOX:
  1048	        raise RuntimeError("callback delivery not configured")
  1049	
  1050	    def clean(v, limit):
  1051	        # Drop unresolved Bland template placeholders ("{{store}}") so they never
  1052	        # appear literally in a staff email.
  1053	        s = str(v or "").strip()
  1054	        if re.fullmatch(r"\{\{.*\}\}", s):
  1055	            s = ""
  1056	        return s[:limit]
  1057	
  1058	    msg = clean(body.get("message"), 4000)
  1059	    if not msg:
  1060	        raise ValueError("message is required")
  1061	    if len(str(body.get("message", "")).strip()) > 4000:

  1064	    caller = clean(body.get("caller_name"), 120)
  1065	    callback = clean(body.get("callback_phone"), 40)
  1066	    intent = clean(body.get("intent"), 120)
  1067	    kind = clean(body.get("kind"), 32)
  1068	    issue = clean(body.get("issue"), 200)

  1070	    about = issue or intent
  1071	    if is_urgent:
  1072	        header = "*** URGENT EYE EMERGENCY - caller triaged as needs-to-be-seen-fast ***"
  1073	        subject = f"URGENT EYE EMERGENCY - {store} - callback needed"
  1074	    else:
  1075	        header = "A caller left a message with the Classic Vision Care voice assistant."
  1076	        subject = f"CVC callback request - {store}"
  1077	    # Structured, plain-text body. SES 'to' is a CVC-owned inbox (BAA path).
  1078	    # PHI (name / phone / issue) rides ONLY this secure channel (SES + Google Chat).
  1079	    lines = [
  1080	        header,
  1081	        "",
  1082	        f"Office: {store}",
  1083	        f"Caller name (as given): {caller or '(not provided)'}",
  1084	        f"Callback number: {callback or '(not provided)'}",
  1085	        f"About: {about or '(not specified)'}",
  1086	        "",
  1087	        "Message:",
  1088	        msg,
  1089	        "",
  1090	        "-- Sent automatically by the CVC booking assistant. Reply is not monitored.",
  1091	    ]
  1092	    body_text = "\n".join(lines)
  1093	    resp = _ses().send_email(
  1094	        FromEmailAddress=CALLBACK_FROM,
  1095	        Destination={"ToAddresses": [CALLBACK_INBOX]},
  1096	        Content={"Simple": {
  1097	            "Subject": {"Data": subject, "Charset": "UTF-8"},
  1098	            "Body": {"Text": {"Data": body_text, "Charset": "UTF-8"}},
  1099	        }},
  1100	    )
  1101	    gchat = post_google_chat(f"*{subject}*\n{body_text}")
  1102	    sms = "n/a"
  1103	    if is_urgent:
  1104	        sms = "skipped"
  1105	        # The alert fires before the pathway's hours check, so the gateway resolves
  1106	        # office state itself (deterministic) to route the ping: front desk when
  1107	        # open, on-call doctor after hours.
  1108	        state = "after_hours"
  1109	        try:
  1110	            state = hours_state(store, datetime.now(ZoneInfo("America/New_York")))["state"]
  1111	        except Exception:
  1112	            pass

  1114	        if os.environ.get("CVC_ALERT_SMS_ENABLED") == "1" and recipients:
  1115	            try:

  1119	                sms = "sent"
  1120	            except Exception:
  1121	                log.warning("urgent SMS ping failed (secure-channel alert unaffected)")
  1122	                sms = "failed"
  1123	    return {"ok": True, "delivered": True, "email": True, "google_chat": gchat,
  1124	            "sms": sms, "message_id": resp.get("MessageId", "")}

  1265	class _SessionRWLock:
  1266	    """Allow concurrent CLI calls while making session logins exclusive."""
  1267	
  1268	    def __init__(self):
  1269	        self._condition = threading.Condition()
  1270	        self._readers = 0
  1271	        self._writer = False
  1272	        self._waiting_writers = 0
  1273	
  1274	    @contextmanager
  1275	    def cli_call(self, deadline: float | None = None):
  1276	        with self._condition:
  1277	            while self._writer or self._waiting_writers:
  1278	                if deadline is None:
  1279	                    self._condition.wait()
  1280	                else:
  1281	                    self._condition.wait(timeout=_remaining_timeout(deadline))
  1282	            self._readers += 1
  1283	        try:
  1284	            yield
  1285	        finally:
  1286	            with self._condition:
  1287	                self._readers -= 1
  1288	                if not self._readers:
  1289	                    self._condition.notify_all()
  1290	
  1291	    @contextmanager
  1292	    def login(self, deadline: float | None = None):
  1293	        with self._condition:
  1294	            self._waiting_writers += 1
  1295	            try:
  1296	                while self._writer or self._readers:
  1297	                    if deadline is None:
  1298	                        self._condition.wait()
  1299	                    else:
  1300	                        self._condition.wait(timeout=_remaining_timeout(deadline))
  1301	                self._writer = True
  1302	            finally:
  1303	                self._waiting_writers -= 1
  1304	        try:
  1305	            yield
  1306	        finally:
  1307	            with self._condition:
  1308	                self._writer = False
  1309	                self._condition.notify_all()
  1310	
  1311	
  1312	# Any in-process session warmer must use SESSION_LOCK.login() around auth login.
  1313	SESSION_LOCK = _SessionRWLock()
  1314	_RELOGIN_TS = 0.0
  1315	_RELOGIN_COOLDOWN_S = 30
  1316	_DEAD_SESSION_RE = re.compile(r"egweb\.\S* returned HTTP 404")
  1317	_SESSION_LOCK_FILE_DEFAULT = "/tmp/eyecloud-session.lock"
  1318	_SESSION_LOCK_TIMEOUT_S_DEFAULT = 60.0

  1321	@contextmanager
  1322	def _session_file_lock(exclusive: bool = False, deadline: float | None = None):
  1323	    """Take the cross-process session lock, degrading open on failure/timeout."""
  1324	    lock_path = os.environ.get("ECP_SESSION_LOCK_FILE", _SESSION_LOCK_FILE_DEFAULT)
  1325	    try:
  1326	        lock_file = open(lock_path, "a+")
  1327	    except OSError as exc:
  1328	        log.warning("session flock unavailable path=%s error=%s; proceeding unlocked",
  1329	                    lock_path, exc)
  1330	        yield
  1331	        return
  1332	
  1333	    acquired = False
  1334	    operation = fcntl.LOCK_EX if exclusive else fcntl.LOCK_SH
  1335	    try:
  1336	        try:
  1337	            timeout_s = max(
  1338	                0.0,
  1339	                float(os.environ.get(
  1340	                    "ECP_SESSION_LOCK_TIMEOUT_S",
  1341	                    str(_SESSION_LOCK_TIMEOUT_S_DEFAULT),
  1342	                )),
  1343	            )
  1344	        except ValueError:
  1345	            timeout_s = _SESSION_LOCK_TIMEOUT_S_DEFAULT
  1346	        lock_deadline = (
  1347	            time.monotonic() + timeout_s if deadline is None else deadline
  1348	        )
  1349	        while True:
  1350	            try:
  1351	                fcntl.flock(lock_file.fileno(), operation | fcntl.LOCK_NB)
  1352	                acquired = True
  1353	                break
  1354	            except OSError as exc:
  1355	                if exc.errno not in (errno.EACCES, errno.EAGAIN):
  1356	                    log.warning(
  1357	                        "session flock unavailable path=%s error=%s; proceeding unlocked",
  1358	                        lock_path, exc,
  1359	                    )
  1360	                    break
  1361	                if time.monotonic() >= lock_deadline:
  1362	                    if deadline is not None:
  1363	                        raise subprocess.TimeoutExpired("eyecloud-cli", timeout_s)
  1364	                    log.warning(
  1365	                        "session flock wait timed out after %.1fs path=%s mode=%s; "
  1366	                        "proceeding unlocked",
  1367	                        timeout_s, lock_path, "exclusive" if exclusive else "shared",
  1368	                    )
  1369	                    break
  1370	                remaining = lock_deadline - time.monotonic()
  1371	                if remaining <= 0:
  1372	                    if deadline is not None:
  1373	                        raise subprocess.TimeoutExpired("eyecloud-cli", timeout_s)
  1374	                    break
  1375	                time.sleep(min(0.05, remaining))
  1376	        yield
  1377	    finally:
  1378	        if acquired:
  1379	            try:
  1380	                fcntl.flock(lock_file.fileno(), fcntl.LOCK_UN)
  1381	            except OSError as exc:
  1382	                log.warning("session flock release failed path=%s error=%s",
  1383	                            lock_path, exc)
  1384	        lock_file.close()

  1398	def _relogin(
  1399	    env: dict,
  1400	    force: bool = False,
  1401	    deadline: float | None = None,
  1402	) -> bool:
  1403	    # One login at a time with a cooldown: EyeCloud keeps a single session per
  1404	    # user, so stampeding logins from concurrent requests would kill each
  1405	    # other's sessions — the very failure this recovers from.
  1406	    global _RELOGIN_TS
  1407	    with SESSION_LOCK.login(deadline=deadline):
  1408	        with _session_file_lock(exclusive=True, deadline=deadline):
  1409	            if not force and time.monotonic() - _RELOGIN_TS < _RELOGIN_COOLDOWN_S:
  1410	                return True
  1411	            argv = [CLI, "auth", "login", "--headless",
  1412	                    "--store-id", os.environ.get("ECP_STORE_ID", "956"),
  1413	                    "--agent", "--no-input", "--yes", "--reason", "bland-gateway-relogin"]
  1414	            timeout = 120 if deadline is None else _remaining_timeout(deadline)
  1415	            try:
  1416	                proc = subprocess.run(
  1417	                    argv,
  1418	                    capture_output=True,
  1419	                    text=True,
  1420	                    timeout=timeout,
  1421	                    env=env,
  1422	                )
  1423	            except subprocess.TimeoutExpired:
  1424	                if deadline is not None:
  1425	                    raise
  1426	                log.warning("on-demand relogin timed out after 120s")
  1427	                return False
  1428	            _RELOGIN_TS = time.monotonic()
  1429	            if proc.returncode == 0:
  1430	                log.info("on-demand relogin ok")
  1431	                return True
  1432	            log.warning("on-demand relogin failed rc=%s", proc.returncode)
  1433	            return False

  1436	def run_cli(
  1437	    argv: list,
  1438	    env: dict,
  1439	    timeout_s: float | None = None,
  1440	    deadline: float | None = None,
  1441	):
  1442	    # subprocess.run plus two bounded self-heals: the fixed !egweb-404 stderr
  1443	    # signature marks a dead session. The final rung forces a fresh login rather
  1444	    # than accepting the relogin cooldown. Writes are safe to retry: a
  1445	    # dead-session refusal happens before anything is written, and /book keeps
  1446	    # its read-after-write proof regardless. Arbitrary nonzero exits never retry.
  1447	    explicitly_timed = deadline is not None or timeout_s is not None
  1448	    if deadline is None and timeout_s is not None:
  1449	        deadline = time.monotonic() + timeout_s
  1450	    for attempt in range(1, 4):
  1451	        with SESSION_LOCK.cli_call(deadline=deadline):
  1452	            with _session_file_lock(deadline=deadline):
  1453	                proc = subprocess.run(
  1454	                    argv,
  1455	                    capture_output=True,
  1456	                    text=True,
  1457	                    timeout=TIMEOUT_S if deadline is None else _remaining_timeout(deadline),
  1458	                    env=env,
  1459	                )
  1460	        if not _dead_session(proc) or attempt == 3:
  1461	            return proc
  1462	        force = attempt == 2
  1463	        if explicitly_timed:
  1464	            relogged = _relogin(env, force=force, deadline=deadline)
  1465	        else:
  1466	            relogged = _relogin(env, force=force)
  1467	        if not relogged:
  1468	            return proc
  1469	        if force:
  1470	            log.info("retrying CLI call after forced relogin (attempt 3/3)")
  1471	        else:
  1472	            log.info("retrying CLI call after relogin (attempt 2/3)")
  1473	    return proc
