# Compound Engineering Primitives

Use this as Ankit's owned version of the Compound Engineering GO-now. It is a standards implant, not a third-party plugin adoption.

## Fire conditions

Apply for serious non-PHI code/repo/agentic engineering work when any of these are true:
- a task involves implementation across multiple files, repo changes, tests, PRs, deployment prep, or agent-generated code;
- a worker is about to claim fixed/done/complete/ready;
- a fresh-context review, Cross-Review QA, or Hermes Kanban review-required handoff is needed;
- a reusable lesson appears that should compound into a skill, runbook, solution note, or sanitized OB/Work Ledger capture.

Skip for tiny one-line edits, routine lookups, disposable scratch scripts, or any raw PHI/client-sensitive workflow. This skill does not authorize external sends, CRM/EHR/finance writes, deploys, merges, public uploads, or autonomous commit/push/PR loops.

## Core loop

Run: **Plan -> Work -> Review -> Compound -> Repeat**.

### 1. Plan

Before implementation, create or identify a durable yardstick:
- product/requirements contract separated from implementation plan;
- implementation units with stable IDs (`U1`, `U2`, ...);
- expected proof/test for each unit;
- acceptance criteria and explicit non-goals;
- the three decision-residue questions:
  1. What was the hardest decision made?
  2. What alternatives were rejected?
  3. What assumption is least confident?

If no yardstick exists for serious work, make one before changing code.

### 2. Work

Implement against unit IDs. Keep each proof attached to the unit it validates. Prefer the smallest safe diff that satisfies the yardstick.

### 3. Review

Run report-only review by default:
- fresh context when possible;
- reviewer findings cite the original plan/spec/unit, not the builder's narrative;
- reviewer/subagent outputs land in durable artifacts or run comments, not chat-only prose;
- user directives outrank reviewer best judgment; if a reviewer disagrees, it must flag rather than override;
- no auto-apply, merge, deploy, external send, or public upload from review alone.

### 4. Compound

Before saying done, classify the highest true state reached and attach evidence:
- local artifact only / tests passed / committed / pushed / PR opened / merged / deployed / live action taken / blocked / review-required;
- exact commands/tests/evidence;
- missing proof or skipped checks;
- changed files/artifacts;
- reusable lesson, if any.

If the lesson is reusable, update the smallest durable surface: skill patch, run-card line, solution note, or sanitized Work Ledger/OB capture. Do not capture raw secrets, PHI, client-sensitive details, raw IDs, or raw message bodies.

## Hard no's

- Do not raw-install the Every Compound Engineering plugin by default.
- Do not use `bunx @every-env/compound-plugin` unless version parity with the current repo/release is proven.
- Do not trust stale article/install claims without checking the repo/package state.
- Do not use side-effect-heavy flows such as autonomous commit/push/PR/CI as defaults.
- Do not use in PHI/client-sensitive contexts without explicit HIPAA/BAA/data-flow review.
- Do not upload proof/demo artifacts publicly without explicit user approval.

## Required handoff block for serious work

End serious code/repo work with:

```text
Compound proof:
- Plan/spec yardstick: <path/ref or none + why acceptable>
- Units proved: <U-IDs + proof>
- Review: <fresh/report-only review artifact or why skipped>
- Highest true state: <local/tested/committed/pushed/PR/merged/deployed/blocked/review-required>
- Behavior verification: <command/output/ref>
- Decision residue: hardest decision / alternatives rejected / least-confident assumption
- Compound capture: <skill/runbook/OB/none + reason>
```

### Gate assessment

`gate_trustworthy: no`

The current candidate passes, and the check fails against the original, but the printed PASS overstates what was proven.

- The checker does not load the original resolver. It compares against [golden_baseline.json](/mnt/d_drive/repos/mott/gw-temporal-check/golden_baseline.json:1), whose metadata contains only the date, not the original path or hash.
- I independently reproduced all 106 baseline outputs from the specified original at the frozen date. Result: `BASELINE_EXACT_CURRENT_ORIGINAL True`, zero mismatches. So the baseline contents are currently correct, but their provenance is not self-verifying.
- The generator and checker freeze `_eastern_today` to the same date at noon. That is sufficient here because the resolver uses only `.date()`. “Eastern” is descriptive, however; both inject a naive `datetime`, not a `ZoneInfo` Eastern clock.
- Most importantly, [check_gateway_datefix.py](/mnt/d_drive/repos/mott/gw-temporal-check/check_gateway_datefix.py:73) forcibly overwrites `_DATE_ORDINAL_FALLBACK` after import. A candidate with a broken environment binding, ignored environment variable, or wrong default could still pass. The current implementation independently loaded correctly as default `False`, env `0` → `False`, env `1` → `True`, but the gate itself does not prove that.
- The check verifies outputs for 106 inputs. It neither verifies the approved two-hunk source diff nor behavioral equivalence for other inputs. A substantially altered resolver could pass by preserving those cases.
- Missing baseline keys are not rejected as a schema error. `golden.get(p)` can silently treat missing expected-`None` cases as valid.

### Diff safety

`diff_safe: no`, despite being structurally legacy-first.

The actual diff contains only the flag and fallback hunks. The fallback is after every existing successful return, so no input the original already resolves can change. Flag OFF is also inert.

The problem is unintended expansion when flag ON. The regex strips ordinal suffixes anywhere, not only from a month-day expression:

| Input | Original | Flag ON |
|---|---:|---:|
| `22nd` | `None` | `None` |
| `1st` | `None` | `None` |
| `the 2nd tuesday` | `None` | `None` |
| `3rd week` | `None` | `None` |
| `in 2 days` | `07/29/2026` | unchanged |
| `in 2nd days` | `None` | `07/29/2026` |
| `28th days from now` | `None` | `08/24/2026` |
| `2nd weeks from now` | `None` | `08/10/2026` |
| `july 11st` | `None` | `07/11/2027` |
| `july 22th` | `None` | `07/22/2027` |
| `07th/28th` | `None` | `07/28/2026` |
| `07th/28th/2026` | `None` | `07/28/2026` |

Therefore, the claim that only intended ordinal month-day phrases become accepted is false. The implementation accepts malformed suffixes, ordinalized relative counts, and ordinalized numeric dates.

### Corpus gaps

Original-accepted forms missing from `gen_golden.py` include:

- Day-count variants: `3 days`, `in 3 days from now`, `in 0 days`.
- Week variants: `in one week`, `in ten weeks`, `in a couple week`, `in couple week`.
- Chinese `个星期` forms: `三个星期后`, `3个星期后`, `十个星期后`.
- Chinese weekday carriers other than `周`: `星期一`, `礼拜天`, `下星期三`, `下下礼拜日`, `本礼拜六`.
- English abbreviated compound forms: `next mon`, `mon after next`, `the day after thu`, `a week from fri`, `fri next week`.
- Normalization behavior: `TOMORROW`, `tomorrow!`, and repeated/outer whitespace.
- Past yearless rollover: `july 26`, `07/26`, `Jul 26`, which resolve into 2027 at the frozen date.

A drift limited to any of these forms could pass the existing gate.

### Edge and recursion risks

- Infinite recursion: no. One substitution removes every matching suffix in the string. The recursive call cannot perform the same substitution again, so depth is at most two calls.
- Multi-ordinal strings: all matching ordinals are stripped simultaneously. The tested compound `july 28th july 29th` remains `None`, but `07th/28th` and `07th/28th/2026` become accepted.
- Wrong-result risk: material. Ordinal count phrases and malformed suffixes can silently turn a rejected input into a booking date.
- Inflation risk is bounded to two-digit stripped counts, but up to 99 days or weeks can still be introduced.

### Residual CVC risk

CVC runtime risk is low only if CVC is not redeployed or its process lacks the flag. Separate processes and default OFF provide useful isolation.

However:

- `TENANT_ID` does not guard this fallback. The resolver checks only the flag.
- A shared task-definition variable, configuration mistake, future default change, or accidental CVC flag enablement exposes CVC.
- The current checker’s post-import override would not catch several of those configuration failures.
- I did not inspect live CVC/Mott task definitions, image revisions, or process environments, so actual deployment isolation remains unverified.
