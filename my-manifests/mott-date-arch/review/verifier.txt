# Compound Engineering Primitives

Use this as Ankit's owned version of the Compound Engineering GO-now. It is a standards implant, not a third-party plugin adoption.

## Fire conditions

Apply for serious non-PHI code/repo/agentic engineering work when any of these are true:
- a task involves implementation across multiple files, repo changes, tests, PRs, deployment prep, or agent-generated code;
- a worker is about to claim fixed/done/complete/ready;
- a fresh-context review, Cross-Review QA, or Hermes Kanban review-required handoff is needed;
- a reusable lesson appears that should compound into a skill, runbook, solution note, or sanitized OB/Work Ledger capture.

Skip for tiny one-line edits, routine lookups, disposable scratch scripts, or any raw PHI/client-sensitive workflow. This skill does not authorize external sends, CRM/EHR/finance writes, deploys, merges, public uploads, or autonomous commit/push/PR loops.

## Core loop

Run: **Plan -> Work -> Review -> Compound -> Repeat**.

### 1. Plan

Before implementation, create or identify a durable yardstick:
- product/requirements contract separated from implementation plan;
- implementation units with stable IDs (`U1`, `U2`, ...);
- expected proof/test for each unit;
- acceptance criteria and explicit non-goals;
- the three decision-residue questions:
  1. What was the hardest decision made?
  2. What alternatives were rejected?
  3. What assumption is least confident?

If no yardstick exists for serious work, make one before changing code.

### 2. Work

Implement against unit IDs. Keep each proof attached to the unit it validates. Prefer the smallest safe diff that satisfies the yardstick.

### 3. Review

Run report-only review by default:
- fresh context when possible;
- reviewer findings cite the original plan/spec/unit, not the builder's narrative;
- reviewer/subagent outputs land in durable artifacts or run comments, not chat-only prose;
- user directives outrank reviewer best judgment; if a reviewer disagrees, it must flag rather than override;
- no auto-apply, merge, deploy, external send, or public upload from review alone.

### 4. Compound

Before saying done, classify the highest true state reached and attach evidence:
- local artifact only / tests passed / committed / pushed / PR opened / merged / deployed / live action taken / blocked / review-required;
- exact commands/tests/evidence;
- missing proof or skipped checks;
- changed files/artifacts;
- reusable lesson, if any.

If the lesson is reusable, update the smallest durable surface: skill patch, run-card line, solution note, or sanitized Work Ledger/OB capture. Do not capture raw secrets, PHI, client-sensitive details, raw IDs, or raw message bodies.

## Hard no's

- Do not raw-install the Every Compound Engineering plugin by default.
- Do not use `bunx @every-env/compound-plugin` unless version parity with the current repo/release is proven.
- Do not trust stale article/install claims without checking the repo/package state.
- Do not use side-effect-heavy flows such as autonomous commit/push/PR/CI as defaults.
- Do not use in PHI/client-sensitive contexts without explicit HIPAA/BAA/data-flow review.
- Do not upload proof/demo artifacts publicly without explicit user approval.

# Code Reviewer Skill

You are a senior code reviewer. When invoked, you will:

## Mandatory cross-review overlay

For PR reviews, milestone reviews, pre-merge gates, or serious agent-built work, first load `cross-review-qa` and apply its fresh QA loop:
- Preserve the original plan/spec/acceptance criteria and relevant ATLAS SPINE as the yardstick.
- Spawn a brand-new read-only QA context; when the reviewer is Claude Code, call it through `tmux-model-workers`, not `claude -p` or blind background execution.
- Require issue-only findings labeled `BLOCK`/`HIGH`/`MEDIUM`/`LOW`, with file/section evidence and suggested fix direction.
- Send enumerated `BLOCK`/`HIGH` findings back to the main agent/builder to fix, rerun verification, then re-review.
- Keep looping until no `BLOCK`/`HIGH` findings remain before reporting pass/completion.

## Primary Tasks
1. Analyze code for potential bugs and edge cases
2. Check for adherence to best practices and design patterns
3. Evaluate code readability and maintainability
4. Identify security vulnerabilities
5. Suggest performance optimizations
6. Verify proper error handling

## Review Checklist
- [ ] Code follows project conventions
- [ ] Functions have single responsibility
- [ ] Proper error handling implemented
- [ ] No security vulnerabilities
- [ ] Tests cover critical paths
- [ ] Documentation is clear and complete
- [ ] Performance is acceptable
- [ ] No code duplication

### Safety-gate / readiness-lane reviews

When reviewing code that controls go-live, readiness, approvals, external actions, CRM writes, email/SMS/LinkedIn sends, or deploy/merge authority, add an explicit fail-closed pass:
- [ ] Permission booleans fail closed: malformed truthy values like `"false"`, `"true"`, `1`, non-empty lists, or missing keys do not accidentally authorize action or display readiness.
- [ ] Readiness labels are precise: distinguish **artifact ready**, **executor-queue/gate ready**, and **side-effect permission granted**. A Level 4/executor-ready verdict may be valid without opening sends/writes; verify `send_allowed` and `write_allowed` separately.
- [ ] Human-review policy is explicit and tested. If the product rule is threshold-based (for example: human review only after more than 3 QA failures), verify pass/retry/escalate branches and do not preserve stale “QA pass → human approval” assumptions in tests or labels.
- [ ] A ready verdict depends on the actual gate/request/artifact status and current policy, not only on an upstream draft status string.
- [ ] Leak and side-effect scans check both regex payload leaks and explicit safety flags/counters/aliases.
- [ ] Important findings that could change a readiness verdict are treated as pre-finalization fixes, not optional follow-up.

### Live-vs-mock integration readiness

When reviewing integration-heavy work, especially contractor/vendor deliverables, do not treat a passing test suite as proof of production readiness:
- [ ] Inspect adapter selectors and environment gates, not just service code. Look for `*_MOCK`, `validateOnly`, `mock-first`, `developer token pending`, `not configured`, and live-mode branches that intentionally throw.
- [ ] Classify each integration as **live verified**, **live scaffolded**, **mock/stub only**, or **blocked**. A live client class is only “live scaffolded” until a dated external acceptance/read-back artifact exists.
- [ ] Require proof artifacts for business-loop completion: e.g. click → call → confirmation → accepted external conversion, with each step labeled live/synthetic/mock.
- [ ] Call out PR/CI absence separately from code quality; local green checks are useful but do not replace protected branch review and repeatable CI.
- [ ] Treat stale task/spec checkboxes as a governance gap: implemented files may exist, but project status is ambiguous until task docs or release notes match the repo state.

## Output Format
Provide feedback in this structure:
1. **Critical Issues** (must fix)
2. **Important Suggestions** (should fix)
3. **Minor Improvements** (nice to have)
4. **Positive Observations** (what was done well)

Always explain WHY something should be changed and provide specific examples.

## Output Contract

**On success:** Returns a structured review with 4 sections: (1) Critical Issues (must fix), (2) Important Suggestions (should fix), (3) Minor Improvements (nice to have), (4) Positive Observations (what was done well). Each finding includes the WHY and a specific code example or fix.

**On partial success:** If only part of the code could be reviewed (e.g., file too large, binary content), returns findings for the reviewable portion with a note about what was skipped.

**On failure:** Returns an error explaining why the review could not be completed (e.g., "File not found at specified path", "PR #123 does not exist in this repo") with suggested next steps.

- **Rate limits:** No external API calls. Local code analysis only.
- **Blast radius:** Review output is advisory only — no code is modified. Zero blast radius.
- **Cost:** Zero. No external API costs.
- **Permissions:** Requires read access to the files or repo being reviewed. No write access needed.

## Self-Verification

Before delivering output, the skill MUST verify:
- [ ] All 4 output sections are present (Critical, Important, Minor, Positive)
- [ ] Each finding includes a WHY explanation and specific code reference
- [ ] No PHI values are reproduced in the review output (line numbers only)
- [ ] MyBCAT conventions were checked: type hints, f-strings, logging (not print), parameterized SQL, proper error handling, no PHI logging
- [ ] Security review was performed: no hardcoded credentials, no SQL injection, no open security groups
- [ ] Review is actionable — vague feedback like "could be better" is replaced with specific suggestions

If any check fails, do NOT deliver output. Follow the Failure Path instead.

# Cross-Review QA

This skill makes cross-review the default QA gate for serious PRs and milestones. One model/context builds; a fresh QA worker reviews against the original plan/spec; the main agent fixes; the fresh reviewer re-checks. The reviewer must not inherit the builder's excuses.

When the QA worker is Claude Code, invoke it through `tmux-model-workers` in a named tmux session, never as a blind headless `claude -p` call. Codex CLI interactive QA may also use tmux; Codex `exec -s read-only` remains acceptable only when a one-shot read-only review is sufficient and the output is independently captured.

## Core rule

For every PR review or milestone review with maintainable, client-impacting, security/auth/data, production, or multi-file agent-built work:

1. Preserve the original yardstick: plan/spec/acceptance criteria, relevant ATLAS Index/SPINE, task card, and expected tests.

for fmt in ("%m/%d", "%B %d", "%b %d"):

It then advances a past date by one year. See [bland_gateway.py:585](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:585).

Bare `"28"` is **not** accepted. It matches no relative grammar or date format and reaches `return None` at [bland_gateway.py:603](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:603).

2. **Next-non-past month/day is existing logic**

This is not new for ordinary yearless dates. Existing behavior is:

```python
d = datetime.strptime(t, fmt).date().replace(year=today.year)
if d < today:

```

See [bland_gateway.py:590](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:590).

Therefore, ordinal stripping alone can route `"july 28th"` into existing month/day logic. The genuinely new areas are bare days, compounds, conflict handling, and some calendar edge cases.

One existing defect matters: `"february 29"` returns `None` because `%B %d` is initially parsed using default year 1900, which is not a leap year. The design does not define how “next occurrence” handles February 29.

3. **Ordinal collision assessment**

A narrowly bounded substitution such as:

```python
r"\b(1|2|...|31)(st|nd|rd|th)\b"
```

does not collide with any currently accepted token or month name:

- `august` is untouched because `st` is not preceded by a numeric day.
- `thursday` is untouched because `th` is not after a number.
- `in 30 days` is untouched because no ordinal suffix follows `30`.
- Chinese tokens are untouched.

The risk is over-acceptance, not collision. A naive “any suffix after 1–31” regex would convert malformed `"11st"`, `"12nd"`, or `"23th"` into valid dates. The design must either require grammatically correct suffixes or explicitly accept malformed ordinals.

4. **Monday-anchored week branch**

The deployed branch is:

## Evidence

1. **Current acceptance**

`"july 28"` is already accepted. The resolver tries yearless formats:

```python
for fmt in ("%m/%d", "%B %d", "%b %d"):
    d = datetime.strptime(t, fmt).date().replace(year=today.year)
```

It then advances a past date by one year. See [bland_gateway.py:585](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:585).

With `today = 2026-07-27`, the real function returned:

```text
"july 28" -> "07/28/2026"
```

Bare `"28"` is **not** accepted. It matches no relative grammar or date format and reaches `return None` at [bland_gateway.py:603](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:603).

```text
"28" -> None
"28th" -> None
"july 28th" -> None
```

2. **Next-non-past month/day is existing logic**

This is not new for ordinary yearless dates. Existing behavior is:

```python
d = datetime.strptime(t, fmt).date().replace(year=today.year)
if d < today:
    d = d.replace(year=d.year + 1)
```

See [bland_gateway.py:590](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:590).

Verified:

```text
"july 27" -> "07/27/2026"
"july 28" -> "07/28/2026"
"july 26" -> "07/26/2027"
```

Therefore, ordinal stripping alone can route `"july 28th"` into existing month/day logic. The genuinely new areas are bare days, compounds, conflict handling, and some calendar edge cases.

One existing defect matters: `"february 29"` returns `None` because `%B %d` is initially parsed using default year 1900, which is not a leap year. The design does not define how “next occurrence” handles February 29.

3. **Ordinal collision assessment**

A narrowly bounded substitution such as:

```python
r"\b(1|2|...|31)(st|nd|rd|th)\b"
```

does not collide with any currently accepted token or month name:

- `august` is untouched because `st` is not preceded by a numeric day.
- `thursday` is untouched because `th` is not after a number.
- `in 30 days` is untouched because no ordinal suffix follows `30`.
- Chinese tokens are untouched.

The risk is over-acceptance, not collision. A naive “any suffix after 1–31” regex would convert malformed `"11st"`, `"12nd"`, or `"23th"` into valid dates. The design must either require grammatically correct suffixes or explicitly accept malformed ordinals.

4. **Monday-anchored week branch**

The deployed branch is:

```python
def calendar_weekday(weekday, weeks_ahead):
    monday = today - timedelta(days=today.weekday())
    return monday + timedelta(weeks=weeks_ahead, days=weekday)
```

See [bland_gateway.py:500](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:500). Its callers include `next week`, Chinese week forms, `Tuesday after next`, and `Tuesday next week` at [bland_gateway.py:512](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:512) and [bland_gateway.py:559](/home/ankit114/repos/ringer/my-manifests/mott-date-arch/date-design/source/bland_gateway.py:559).

Ordinal stripping itself leaves this untouched. The proposed compound tokenizer does **not demonstrably preserve it**. If tokenization splits multiword atoms, `"tuesday next week"` could become independent `"tuesday"` and `"next week"` cues, changing a currently valid result into a conflict. The design must require longest-match parsing of the existing grammar before compound separation.
