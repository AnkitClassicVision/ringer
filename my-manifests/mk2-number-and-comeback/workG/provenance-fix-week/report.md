## Pathway-side requirements

This is the rebuild checklist for the complete coupled fix set.

1. **Preference extraction fields and prompts**
   - Nodes `n_ask`, `n_date_conflict`, `n_miss_empty`, `n_miss_unread`, `n_miss_thin`, `n_miss_unbookable`, `n_miss_time`, and `n_negotiate` each require `data.extractVars` entries, in the healthy graph, for: `user_verbatim`, `preference_from`, `day_part`, `time_after`, `preference_to`.
   - `n_clarify` requires `user_verbatim`, `preference_from`, `preference_to` (it intentionally omits time fields via `WINDOW_VARS`).
   - `user_verbatim` prompt: copy the entire most recent USER message exactly, preserving spelling/shorthand/punctuation, with no interpretation.
   - `preference_from` prompt: preserve week qualifiers (`wednesday next week`), expand shorthand, copy explicit month/day, never compute a weekday, treat busy/negated dates as context, use `tomorrow` for ASAP-family requests, and never emit null.
   - `preference_to` prompt: mirror a single day including qualifiers; form ranges (`friday next week`, `sunday next week`); never compute dates; never emit null.
   - `day_part` prompt: output exactly `morning|afternoon|late|outside|none`; `late` begins at 3pm; rejected/context-only bands do not become requests.
   - `time_after` prompt: output a normalized 12-hour clock time or `none`; phrases such as “after 2,” “not before 3,” and “busy until 2” produce the lower bound.

2. **Availability webhook request bodies**
   - On `n_search`, `n_page_2`, `n_page_3`, `n_page_near`, retain: `store`, `from:"{{preference_from}}"`, `to:"{{preference_to}}"`, `after:"{{time_after}}"`, `before:"none"`, `time_pref`, `slot_minutes:"15"`, `callID:"{{callID}}"`, `user_text:"{{lastUserMessage}}"`, `user_verbatim:"{{user_verbatim}}"`.
   - Exact `time_pref`: `none` on `n_search`; `afternoon` on `n_page_2`; `late` on `n_page_3`; `afternoon` on `n_page_near`.

3. **Availability response mappings and routes**
   - All four nodes: `ok`, `slot_count`, both slots' `start`, `end`, `doctor_id`, `day_name`, and `time_pref_relaxed` with the JSONPaths shown in v65.
   - `n_search` additionally requires `conflict_option_1: $.result.date_conflict[3]`, `conflict_option_2: $.result.date_conflict[4]`, `date_conflict_detected: $.result.date_conflict[0]` and the conflict route before slot-count routing.
   - Preserve page 2/3 relaxed-band routes to `n_offer_near`, plus `day_part` routes from `n_search` to page 2/3.

4. **Patient-facing prompts/nodes**
   - `n_date_conflict`: exact two-option prompt using `{{conflict_option_1}}` / `{{conflict_option_2}}`, full preference extraction, edge back to `n_search`.
   - `n_offer`, `n_offer_2`, `n_offer_3`, `n_offer_near`: both English and Chinese copy and all prompt context must include gateway-supplied `slot_1_day_name` / `slot_2_day_name`; never let the model invent weekdays/times.
   - `n_help`: all global/auto-return fields and exact help prompt described in the inventory.

## WIRING

1. Bland maintains the conversation identifier as `{{callID}}`. Each availability webhook serializes it into the JSON body as `callID` alongside the model-extracted date/time fields.
2. `clamp_availability_range` unconditionally pops `callID`, so it never leaks into the downstream CLI argument builder. When raw-text dates are enabled, the tenant normalizes to exactly `mott`, the ID is valid, and this is not a `first_available` request, the gateway uses that ID to fetch the Bland conversation transcript.
3. `_fetch_conversation` requires `ECP_BLAND_API_KEY`, refuses redirects, caps reads, and tries Bland's SMS conversation endpoint followed by the pathway-chat endpoint within one deadline. The returned `messages` or `chat_history` list is normalized.
4. `_latest_user_text` chooses the newest USER by `created_at` only when all USER messages have timestamps; otherwise it chooses the last USER in list order. Parsing is capped at 2,000 characters.
5. Deterministic raw parsing produces a date, range/ASAP, conflict tuple, or no result. A date/range can replace model-derived `from`/`to`; a conflict is exposed as `date_conflict` while model `from`/`to` remain intact; no result or any fetch/parser error leaves the model extraction as fallback.
6. If enabled, the v2 Bedrock tier sees the same latest text and may return only an operative phrase. The gateway validates the phrase and sends it through `extract_date_from_text`; deterministic-first precedence and fail-open behavior remain.
7. The availability envelope returns real slots with code-computed `day_name`, time-band relaxation, and any conflict tuple. Bland maps those response fields, routes conflicts to `n_date_conflict`, or renders weekday-labelled offers. Thus `callID` is the provenance bridge: conversation → webhook body → transcript lookup → deterministic/LLM-refereed intent → safe response variables.
