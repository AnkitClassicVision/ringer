# FINDINGS

### Finding 1: Stale higher-level discovery receipts survive a subsequent lower-level `verify` call
Evidence: `scripts/implant_skill.py:1081` (`existing_receipts.setdefault(surface, {})`) and `scripts/implant_skill.py:1132-1138` use `dict.setdefault` to fill in levels above the requested `--level` with `NOT_RUN`, which only takes effect if that key is absent. A prior `verify --level invoked` run that wrote a real `passed: true` receipt for `loaded`/`invoked` is never overwritten by a later `verify` call made at a lower (but still ≥ `minimum_discovery_level`) level. No test in `tests/test_implant_skill.py` or `check_implant_workflow.py` issues two `verify` calls at different levels against the same manifest, so this path is unexercised.
Impact: An operator or an automated consumer reading `receipts.targets.<surface>.invoked` after a fresh, narrower verify can see a `passed: true` entry that was not re-checked in that run and may now be false (e.g. the harness later stopped loading the skill). Combined with `status: VERIFIED` on the manifest, this creates a false impression of currently-proven discovery at a level the run did not actually test — directly contrary to the brief's "no stale discovery receipts" and "existence-only red case must remain red" intent generalized to "un-run levels must read as not run."
Fix: Always overwrite every level above `required_index` with the `NOT_RUN` placeholder (plain assignment, not `setdefault`), and add a replay test that runs `verify --level invoked` then `verify --level loaded` (or `present`) on the same manifest and asserts the `invoked` receipt becomes `NOT_RUN` rather than retaining its earlier value.
Priority: High
Confidence: High (direct code trace; deterministic, not timing-dependent)

### Finding 2: The JSON manifest schema is unenforced and not proven to match the runtime validator
Evidence: `scripts/validate_implant_manifest.py` (whole file) never references `assets/implant-manifest.schema.json`; `scripts/implant_skill.py` never references it either (confirmed by repo-wide grep — the schema file and `IMPLEMENTATION_SPEC.md` are the only two files that mention it). `check_implant_workflow.py:165-174` only checks `path.is_file()` for the schema and template, never loads or validates against them. A concrete divergence exists today: `assets/implant-manifest.schema.json:52-89` (`$defs.pathState`) only requires `path`, `exists`, `kind` and does not encode the "if `kind == link` then `link_target` is required" conditional, while the runtime validator enforces exactly that conditional and rejects a manifest missing it (`scripts/implant_skill.py:625-650`). The schema is therefore looser than the code it is supposed to describe, and nothing would catch further drift.
Impact: The mission contract's U1 requirement ("strict validator/schema/template parity") is asserted by the presence of the file, not demonstrated by any check. A future edit to either the schema or `_validate_plan_shape`/`_validate_path_state` can silently diverge with no test failure, and any external tooling (CI, IDEs, other harnesses) that validates against the published schema could accept manifests the runtime script would reject, or vice versa.
Fix: Either (a) add a lightweight stdlib-only structural check that asserts the schema's `required`/`enum`/`pattern` constraints for each `$defs` block match the corresponding Python validation rules (a data-driven test, not a full JSON Schema implementation), or (b) generate the schema file from the same constant tables the Python code already uses (`TARGET_PLAN_KEYS`, `LEVELS`, `COLLISION_ACTIONS`, etc.) so drift is structurally impossible. Also add a smoke test that loads `assets/implant-request.template.json` through `build_plan()` to guarantee the template stays accepted by the parser it documents.
Priority: Medium
Confidence: High (confirmed by grep across the entire review-source tree and direct comparison of the two artifacts)

### Finding 3: No explicit guard rejects a target that aliases the canonical source path
Evidence: Grep of `scripts/implant_skill.py` for any comparison of a target's `destination`/`effective_destination`/`root` against `_source_path(plan)` returns no matches other than the backup-root-vs-source/backup-root-vs-destination checks at `implant_skill.py:807-813`. Nothing stops a request where `root == source.parent` and `destination_name == source.name` (i.e., the target *is* the canonical source directory). Tracing the `REPLACE` path for this case shows the apply transaction currently survives it safely only as an emergent consequence of unrelated logic: the prior-destination move into backup succeeds, the subsequent `os.symlink`/`shutil.copytree` at the now-vacated source path either dangles or raises `FileNotFoundError`, and the post-loop `_check_source` re-hash (or the copytree exception) triggers the existing generic-exception compensation path, which moves the backup back over the original location before failing closed. This was verified by full code trace, not by execution, and by grep confirming no test exercises `root == source.parent`.
Impact: Today's behavior does not appear to corrupt the canonical source, but the protection is incidental — it depends on the exact ordering of `mutations.append()` relative to the operations that can fail, and on `_check_source`/`copytree` happening to raise before anything unrecoverable occurs. A future refactor of the apply transaction (e.g., reordering steps, batching backups, or changing how `mutations` entries are recorded) could silently remove this protection and let a `REPLACE`-classified self-aliasing target destroy or relocate the read-only canonical source, which is the one invariant every other control in this workflow is built to protect.
Fix: Add an explicit `SOURCE_TARGET_OVERLAP`-style check in `build_plan`/`_validate_plan_shape` (or as an apply-time preflight beside the existing backup-root overlap checks at `implant_skill.py:807-813`) that fails closed whenever a target's `destination` or `effective_destination` resolves to the same path as, or is an ancestor/descendant of, the canonical `source` path. Add a unit test constructing exactly this request shape for at least the `REPLACE` and `RENAME` actions.
Priority: Medium
Confidence: Medium (reasoned from a full code trace of the failure/compensation paths; not confirmed by running a reproduction, since the review boundary limited Bash execution to the two named test commands)
